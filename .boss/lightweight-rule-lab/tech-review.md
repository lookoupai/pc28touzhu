# 轻量规则实验室技术评审

## 摘要

- **结论：通过设计评审，进入分波实现。** 采用既有 Python/WSGI、原生页面、独立 SQLite 和一个受限 worker，首版范围可落地，无新增运行依赖。
- 两套 OK 结算、固定金额单腿、管理员且按批次所有者隔离符合本轮需求；历史回放与前向模拟必须在存储和页面同时区分。
- 评审发现的公开范围、数据可见性、合法状态更新、三球校验和历史扫描问题已经由 Architect 修订到架构，当前无未解决的设计阻塞项。
- 生产结算函数本身把单注净利四舍五入到两位小数；模拟须调用同一函数后转整数分累计，不能另造理论精度。
- 后续门禁重点是无未来数据、事务幂等、暂停后待结算处理、资源限额与真实浏览器流程；设计通过不代表实现已通过这些检查。

## 2. 已解决问题与实现约束

| ID | 严重度 | 原问题 / 触发方式 | 已确定的修正与验收 |
|---|---|---|---|
| TR-1 | Major | `share_level != stats_only` 会允许未知分享状态 | 仅 `records` / `analysis` 白名单，且 enabled、share_predictions 都满足；创建与新决策时复核；不读取凭证字段 |
| TR-2 | Major | 字段清单缺少结果和值，无法验证三球与和值一致 | 源读取明确包含 result_number，三个整数均在 0..9 且和一致，否则跳过并记录原因 |
| TR-3 | Major | 将所有输入字段一起哈希，会把 pending→settled 当作冲突 | 哈希只覆盖不可变输入；status/settled_at 可单向补充，方向/号码变化才标记冲突；已结算旧账不自动改写 |
| TR-4 | Blocker（已修订） | 历史特征只按开奖结果发生时刻或预测结算时刻筛选，可能使用延迟到达开奖 | 预测 created_at、settled_at 与开奖 source_created_at 均按各自用途检查；当前目标结果绝不进入条件；缺期不能跨越拼接 |
| TR-5 | Major | 源库无 open_time 索引，日期过滤后 LIMIT 仍可扫描大量数据 | 先沿 issue 索引 keyset 取最多200行，再内存过滤日期；暖机同样分页；不使用 CAST 全表排序，不在 API 中扫描历史 |
| TR-6 | Major | 为保持高赔率精度另算1.846，或提前把赔率改成2.85，会偏离生产口径 | 原始赔率保持2.846，生产 `resolve_pc28_settled_hit_detail()` 返回净利1.85；按返回值转整数分，不在累计层反复浮点舍入 |

TR-1～TR-6 的契约已由 Architect 更新。实现必须覆盖这些触发场景，不能仅以正常路径测试代替。

## 3. 实现风险与对应证据

| 风险 | 等级 | 触发条件 | 必需应对 / 测试 |
|---|---|---|---|
| 回放冒充前向 | 高 | 重启后将已开奖的旧预测按 created_at 补成新决策 | 前向只冻结当前观察到的 pending 且目标为下一期；记录本机 decided_at，开奖后复核40秒；迟到标 skipped，不计下注 |
| 重复入账 | 高 | 提交前异常、进程重启、重复 poll、明细清理后重跑旧页 | 决策唯一键、游标与统计同事务；长期游标/统计不能随短期明细删除；故障注入后重放净值不变 |
| 暂停竞态 | 高 | API暂停与worker计算交错 | 提交新决策前重查batch状态/版本；暂停后拒绝新决策，原pending继续结算；状态修改不可被旧checkpoint覆盖 |
| 冻结规则失效 | 高 | 后续目录赔率或退本规则变化 | 保存完整结算snapshot，结果判定和收益计算都传冻结值；用改变目录后的回放测试验证 |
| 过期或缺失输入 | 中 | 上游已清理、暂停很久、缺三球、日期范围只有部分可用 | 明确计数和范围；缺期重置，窗口不足不判低命中；恢复所需输入缺失给可操作原因，不补造数据 |
| 全局额度被并发突破 | 中 | 多用户/重复按钮同时创建或启动 | 500总实验、100运行实验在写事务中检查；已暂停pending仍受有界清算调度，不能形成无界循环 |
| 大库查询阻塞主服务 | 中 | 在选项、详情或页面请求中导入历史 | API仅配置及有界查询；源只读短连接、查询超时；historical只在worker处理 |
| 存储预算失效 | 中 | 只计主DB忽略WAL/临时文件，或长读取阻止checkpoint | 统计目录文件、WAL预留、主DB页限额；保留暂停写入余量；批量清理保护pending，不做VACUUM |
| 规则容量耗尽 | 低（已知首版限制） | 达到500个已保存实验 | 明确返回 capacity_exceeded；首版不提供自动删除历史实验，不得静默淘汰或隐藏；后续归档能力另迭代 |

资源控制是服务级总预算，不按批次或用户成倍增加。单进程 `CPUQuota=20%` 等于0.2核；不是总机20%，也不保证没有任何瞬时CPU波峰。256MiB为硬限制，必须用原子checkpoint承受进程被终止。1GiB为模拟目录预算，不含系统共享journal；文档不能混淆。

## 4. UI / API 一致性

已对照 UI 和架构：路径、CreateBatch字段、201创建响应、固定50/78实验数量、直接对象响应、错误结构、live/backtest、批次状态及有界详情一致。默认保存暂停、用户启动、手动刷新、CSV只导出当前汇总，符合低资源目标。

UI不展示不存在的三球或置信区间字段，不把 `updated_at` 当开奖截止时间，不把方向命中当实赔。当前金额默认1与生产整数分舍入是可见策略参数，改变下注额需新建批次，不能把不同注额结果线性缩放。

UI文档中自建需求编号与PRD存在文字追溯差异，已交UI角色同步到PRD原编号；这是文档修正，不改变接口或实现范围。

## 5. 实施结论与门禁

设计层无未解决 Blocker。实施按 `plan.md` 的分波里程碑推进；Scrum 在派发前必须把 Python 跨模块接口签名与文件 owner 写入任务规格，尤其源记录、store原子提交、worker单步入口。避免各实现者自行猜测接口。

本轮功能的可逆代码、独立新数据库、API与受限worker配置属于用户“可以……没有的话就可以做”的授权范围；主代理已完成备份前置检查。无主库迁移、无实盘配置写入、无消息发送。文件数较多不构成重复询问用户的理由。

实现验收至少包括：领域/存储/源/worker/API回归；真实本地浏览器创建→启动→暂停→详情→导出；新增模块覆盖统计；50/100/500候选离线性能及少量生产源只读解析。未运行的检查必须明确未运行，不能从基线通过推断新增功能通过。
