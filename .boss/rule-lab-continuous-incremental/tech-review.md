# 实验增量续算技术评审

## 摘要

- **评审结论**：有条件通过，允许进入实现；下列正确性门禁全部通过后才允许开放生产续算。
- **主要风险**：历史结束时的未来结算污染、源明细缺失被误判无预测、比较组使用不同输入版本、普通缓存清理破坏长期续算。
- **必须解决**：R1～R8。既有只读预检不等于实现完成，不允许只清除 completed 或修改原批次 end_date。
- **实施规模**：高 Blast Radius，涉及新增实验库结构、运行状态、API 和报告；保持既有依赖、权限和部署结构。用户已明确授权开发，按父任务授权完成可逆实现及验证，不因文件数重复索要许可。
- **技术债务**：历史基线缺少完整不可变输入清单，只能标注“迁移审计基线”；不能回填一个哈希冒充运行时已验证的历史证据。

## 3. 技术风险评估

| ID | 风险与现有证据 | 等级 | 必须采取的措施 |
|---|---|---|---|
| R1 | worker `_finish_backtest` 和 tick 的 replay_complete 路径按现实时间清 pending | 阻塞 | 连续模式使用持久化事件时间前沿；段末允许 pending；全局 sweep 也遵守前沿；不将未来结果用于下一段更早决策 |
| R2 | `_replay_backtest`、`_settle_pending` 读取上游，`_history` 读取普通缓存 | 阻塞 | 连续模式全部输入路径统一使用段冻结档案视图，包括暖机、待结算、evidence；上游删除 A 后只能读本地 A 边界与已采集 B |
| R3 | `get_predictions` 缺行只返回空，不能区分源已清理和真实无预测 | 阻塞 | 采集覆盖必须逐期记录成功读取、无可用预测、非法、待重查、archive_gap；结合上游归档日期/最早保留边界，无法证明时保守阻止，不伪造完整性 |
| R4 | cache 同一期变化只标 conflict，不能固定比较组使用版本 | 阻塞 | 输入版本不可变，预测 pending→settled 也是新观察版本；段冻结 archive_revision 与共同 cutoff，所有子批次共享；晚发现修订保留新版本，不改已消费清单 |
| R5 | prune 只保护 running 暖机，暂停超过90天可能失去依赖 | 阻塞 | 保护所有 series 的边界100期、pending、未消费及活动段；捕获/计算暂停独立；不能为腾空间删掉所需数据 |
| R6 | 原 completed 禁重启、运行容量100/保存500，study 队列以 child completed 判断全完成 | 阻塞 | 新段不创建实验；同 series 一个活动段；组原子排队、按现有槽依次计算；等待采集/次日不占运行槽 |
| R7 | 月报窗口由原 end_date 限制，报告读库可能在运行中做不公平比较 | 阻塞 | 累计报告使用有效累计截止；旧 end_date保留；段报告冻结快照；组仅同一共同完成段可比；pending/coverage/time_complete 分开 |
| R8 | schema v3 拒绝未知版本；目录预算只数第一层文件 | 阻塞 | schema v4 加法迁移、旧列逐行一致验证；完整目录计量；冷数据优先用 SQLite 压缩 BLOB，避免额外外部文件提交协议 |
| R9 | 来源 DB 没有受控不可变实例 UUID | 中 | 档案保存配置的稳定源实例 key、预测器ID和内容哈希；来源身份变化需重新确认，不以可变文件mtime当身份 |
| R10 | 无限暂停/任意历史新策略重测在固定预算下不能保证 | 中 | 明确24个月为有配额的档案保留目标；未消费数据优先保护；空间不足显示采集暂停及缺口风险，不承诺无限存储 |

## 4. 技术可行性分析

### 4.1 核心功能

单批次/比较组续算、每日自动追加、手动追加、分段与累计报告均可在当前单体完成。先验证数据/事件时间契约，再接 UI；不重新设计赔率或风控公式。

### 4.2 需要落实的技术选择

- 段状态和累计账本的事务边界放在 store；worker 不自行更新资金或日风险。
- 采集每页原子保存输入版本与覆盖，成功后才推进 covered watermark；highest_seen 单独保存。
- 保留 active_round、连亏、资金高点、日风险和 pending；检查点不是只保存 net_cents。
- 旧基线若最后已结结果的可见时刻晚于下一决策时刻，明确拒绝；不尝试从日汇总倒推旧状态。
- 档案以 SQLite 内不可变版本 + 可压缩 payload 实现冷暖层；压缩只改变物理存储，版本/哈希/查询结果不变。

## 5. 架构改进建议

### 5.1 必须修改

R1～R8 必须进入 tasks 的红测、绿门禁和 Stop Condition。尤其需要实际运行分段等价性 fixture，不用只读预检测试代替。

### 5.2 建议优化

界面使用“保留后续数据”“自动续算”“立即追加”“已计算至”，异常只显示实际受影响范围。后端返回结构化质量分类，前端不自行推断连续或完整。

## 6. 实施建议

1. 数据与生命周期：v4、基线、请求幂等、分段、检查点、档案、覆盖与保留。
2. 引擎：采集和 due 调度、冻结输入 adapter、事件时间续接、组队列、重启恢复。
3. 服务和 UI：严格接口、有效报告窗口、历史段读取、可操作的等待/阻塞状态。
4. 独立 QA：全量/分段等价，源删除、修订、晚结算、跨月、幂等、权限、资源、生产一致副本。
5. 部署：备份独立实验库，默认关闭所有现有 series 的自动采集/计算；发布不自动重跑或创建实验。

## 7. 代码规范与职责

采用仓库已有 snake_case Python、既有原生 JS 风格；不得按通用 TypeScript 模板引入新命名体系。Data owner 独占 store、source/档案模型与对应测试；Engine owner 独占 worker；API owner 独占 service/API/月报集成；UI owner 独占 HTML/JS/CSS 和浏览器 fixture。共享文件通过依赖顺序交接，不能并行落盘。
