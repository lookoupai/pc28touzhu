建议：把一个实验做成持续维护的固定策略版本。首次回放完成后，后台持续保存后续精简输入，每天只追加尚未计算的期数，月报从累计账本自动分月生成。旧月份成绩与续算断点长期保存，上游删除预测明细不再迫使同一实验重跑。

推荐默认频率：每分钟采集，每日北京时间 00:10 追加至前一日，月度报告自动更新。具体频率是拟议产品默认值，本次没有创建定时任务、启用采集或启动实验。后续可增加小时级追加，底层仍使用同一段机制。

2. 用户看到的行为

  1. 对现有已完成批次点击“开启自动更新”。预览展示已计算日期、下次起点、26 个原版本、冻结赔率/注额/风控、输入覆盖及空间估算。
  2. 一次开启后，后台先保留新数据，再自动追加计算；无须每月新建实验或手动点“全量运行”。
  3. 每次只计算新期数。10 月完成后固定保留；11 月继续累计；到 12 月自动多出 12 月行，累计曲线自然延长。
  4. 支持“暂停计算，继续收集数据”和“停止自动更新及采集”两个明确操作。暂停计算不等于停止保留后续数据；共享来源仍被其他实验订阅时也不会因一个实验关闭就停止采集。
  5. 改变注额、条件、赔率或风控时，创建新策略版本。已有“金额重测”继续使用独立新版本，但可从长期精简档案读取输入，不强依赖上游仍保留旧明细。
示例：同一个实验持续积累
首次：计算 10-01 ～ 11-26，保留原 26 个版本。
首次追加：仅计算 11-27 ～ 新截止日。
12 月：每天增加上一日的新期数；10 月、11 月历史成绩继续可查。
新增的是计算段和数据，不是每月复制 26 个实验。

区分三个日期：数据采集至、实验计算至、结果结算至。三者不同步时展示实际积压或待结算，不能只显示一个“已完成”。

3. 三条独立流程

上游滚动明细→精简输入档案→新段增量回放→累计账本 / 月报

采集负责保存证据，计算负责推进策略，报告负责读取成绩。采集不能只在实验运行时发生；报告读取不触发计算；实验室继续与真实投注账本和发送任务隔离。

沿用单个 rule_lab_worker、SQLite 和现有资源限额。worker 内按持久化的到期时间调度采集与追加，不引入外部 cron、消息队列或新增运行进程。每个 tick 先给采集一个小预算，再公平轮转计算；单组慢计算不阻塞其他来源保留数据。

建议每分钟检查已订阅来源，每页最多 200 条，延续约 250ms 的源查询预算与 2 秒 worker 工作预算。历史首次补齐和大量重算均拆页；100 个同时运行/500 个保存版本的现有限额继续执行。自动更新等待下一天时不占用运行槽，只在实际计算段排队时占用。

4. 上游删明细前，保存足以计算的精简输入

4.1 保存什么

资料必要字段共享方式
开奖源实例标识、彩种、期号、三球、开奖时间、源记录创建/可见时间、首次观察时间、内容哈希与修订版本。同一期存一份，多个来源与所有实验共用。
预测源实例、预测器身份/配置版本、期号、大小/单双/组合方向、创建/结算时间、状态、首次观察时间、内容哈希及观察版本。同来源同一期存一份，不按 26、78 或 92 个实验重复存。
覆盖记录检查区间、最后成功读取、是否找到记录、无预测/晚预测/失败/源不可读/清理缺失、证据截止、重查状态。覆盖状态按来源与期号索引；缺期本身也保留证据。
不可变输入清单每段实际使用的版本集合/内容摘要、期号范围、行数、质量统计、上段摘要。所有比较子方案共用同一清单；不能各自读到不同源修订。

不复制 API 密钥、提示词、模型大段回答、原始网页或整个上游数据库。当前实验算法依赖的方向、三球与可见时间要保留；只存输赢或日命中率不够。

4.2 采集不是“记住最大期号就完成”

  • 分开保存 highest_seen_issue 与 covered_through_issue：见过后面的数据，不等于中间数据齐全。
  • 新期顺序抓取，同时维护 pending、缺失及修订重查队列；源网络/锁错误不能推进“已覆盖”游标。
  • 近期重查窗口建议 1 日，pending/已记录缺口不受该窗口限制。增加源保留窗口内的低频分区核查，防止晚补旧期只因期号低于高水位被忽略。
  • 源已有 pc28_history_revisions，但只是部分 settled 记录变更计数，不是逐行变更日志；不能据此认定完整 CDC，也不能仅靠它发现 pending 修改。
  • 第一次开启时先导入实验室已有缓存，再补当前源仍有的所选区间。按原数据删除期限优先保留最早即将过期的所需预测，同时留出预算保存最新数据。

4.3 处理数据缺失和修改

三种情况分开：源正常可读且该期确实没有可用预测，按已有缺预测规则跳过并记录；采集失败但源仍可提供，自动重试；所需区间已被上游清理且本地没有证据，则标记 archive_gap，不能伪装成“当时无信号”或零收益。

已被计算段引用的输入版本不可覆盖。后发现修订，增加新版本与冲突记录；原实验保持当时冻结口径，另行明确重算才使用新版本。增量结果保证与同一份冻结输入全量计算一致，不保证与未来上游改写后的数据一致。

保留 source_created_at / source_updated_at / observed_at 的区别。启动前回填的历史输入只能标为回顾性数据；后来采集到的预测不能倒签首次观察时间，声称在开奖前真实观察到了它。

5. 原实验 ID 不变，每次追加一个计算段

新增段记录：segment_id、前段、原实验配置哈希、起点检查点、新截止期/可见截止、输入清单、开始/结束状态、增量统计与结束检查点。原 experiment_id、累计成绩和日账不重置。

原批次的首次 start_date/end_date 作为基线保留，持续区间由 series 的已计算边界与 segment 的目标区间表达。worker 获取当前 work item 时使用当前段的有效区间；报告展示长期累计范围及可选择的历史段。不能只修改原 end_date、清除 replay_complete，再沿用旧 cutoff。

启用自动更新 → 生成一次基线快照
每天到期：
  1. 固定本次已归档的输入版本和目标截止。
  2. 确认上段执行所有权/输入覆盖，创建唯一新段。
  3. 从上次实际已处理期号的下一期开始，读取本地归档。
  4. 每页事务写：逐期决策/结算 + 累计/日账 + 风控状态 + 游标。
  5. 完成后保存新检查点，等待下一次增量。
重启/重复触发：继续原段，不重复创建、计数或结算。
  • 唯一约束确保同一批次只能有一个活动段；request_id + revision 保证 API 与 worker 并发幂等。没有新期数时返回“已追平”，不建空段。
  • 检查点包含资金高点、最大回撤、当前/最大连亏、累计统计、全部实验的运行中轮次、日风控、冷却起点、last_decided/last_settled/last_processed、模拟时钟和未结算事件。
  • 同时保存本来源最后 100 期完整暖机窗口及哈希。暂停/完成的长期实验也必须保护此窗口，不能只保护当前 running 批次。
  • 累计区间可超过 90 天；现有一次回放 90 天上限改为单次追加/分片工作上限。金额重测新版本读取长档案时也分段执行，不能再用原单批区间校验拒绝整个长期区间。
  • 失败只回滚当前页。恢复必须同时核对数据库 revision、引擎兼容版本和检查点摘要，不能依赖内存或前端回传的资金。
  • 后台抓取输入和回放消费分离：长期实验的历史、暖机、目标预测及 pending 结算全部通过本地版本档案读取。只加采集表而仍在 _settle_pending 直接读取上游，不能解决清理后的续算问题。

比较组

单批次和 study 使用同一段机制。比较组一次固定共同的新截止和输入清单，子方案在现有运行槽限制下依次计算；组内禁止某个子批次独立延长。所有子方案完成同一段后，才发布“当前可比”的差值。运行中展示各自进度和上一共同完成段，不能把快方案的 12 月成绩与慢方案的 11 月成绩直接相减。

6. 保证结果正确的时间与版本边界

6.1 跨日/跨月延续真实状态

月初不重置累计回撤、连亏或未完轮次；日风险按真实北京时间开奖日切换，旧日迟到结果仍归旧日。单月收益可以从日账汇总，累计最大回撤不能把各月最大回撤相加，ROI 也不能平均各月百分比。

当前 _finish_backtest 会用较晚参考时间清算最后 pending。直接将 completed 改 running 可能让更晚已知的结算影响新段更早的决策。新段模式必须保存可继续执行的事件时钟前沿：决策、开奖可见、预测结算按各自时间处理，不能在段末按现实现在强制清空 pending。

段末允许保留 pending/活动轮。最多处理到“下一条尚未计算的决策之前”的结算事件；下一条决策时点无法确定时，保存当前模拟时钟和 pending，交给下段逐时推进。月报可以显示“已算完区间，部分结果待结算”，不能为了月末显示完成而把续算状态推进到未来。

6.2 固定策略身份

策略身份由来源身份/配置版本、玩法、条件完整 JSON、单注金额、冻结赔率、风控与算法语义版本共同确定。展示名称不参与关键身份；目录赔率、综合模板后来增加门槛，都不能悄悄改变原 26 个实验。

修正赔率、修改金额或增加条件属于新版本，使用共享输入重测新版本即可，已有稳定版本继续增量。算法修复若改变历史决策口径，旧结果保留明确标记；经兼容验证才能沿用检查点，否则建立新版本。历史上已标记 review_required 的旧回放不能无条件接管并宣称可信。

6.3 月报完整性

分别返回 time_complete（时间区间处理完）、pending_count（待结算）、coverage_quality（完整/有已知跳过/丢失/冲突）和 comparable（同组同输入同段）。原有 missing_prediction 不随功能升级消失；已知相同缺样的两方案可说明“相同样本可比”，不能称为整月输入无缺失。

已完成月份生成带版本号的报告快照，之后新增月份不覆盖它。确需修订旧月，生成新报告 revision 和变更原因，旧快照仍可查。

7. 控制空间：结果长期留，输入精简留，细节有界留

层级建议保留可清理条件
实验定义、日/月汇总、累计状态、段摘要、必要检查点长期保留；检查点压缩并按月/关键边界保留完整版本。明确删除整个实验时才按归属处理；不能被普通明细清理顺带删除。
当前暖机窗口、pending、未消费输入一直保护到不再依赖。所有订阅消费者已处理，且不属于任何暖机、pending、正在提交的段或修订审计。
所选来源精简逐期档案默认建议至少 24 个月；近 90 天热数据，较早按月压缩归档。超过明确保留窗口且无消费/检查点依赖才可回收。若希望更长时间新建策略重算，可在容量预览后延长。
逐笔实验明细与已闭轮细节优先保留最近 30 天，受独立明细配额限制；日期口径仍为实际 finalized_at。已汇总、已归档必要证据、不是 pending/边界审计依赖时回收；空间不足可缩短“可查细节”，不得删累计成绩。

两种保证要分开：固定旧实验依靠检查点和新增输入可持续累计，不必永久保存它已经消费的所有逐期输入；以后新建不同策略要完整重测旧年月，则必须仍保留那些年月的精简输入。24 个月是拟议默认值，不等于永久支持任意历史重测。

7.1 现有数据给出的容量量级

本次用实验库 dbstat 计算表和索引占用：预测约 223.5 字节/条，开奖约 197.8 字节/条。按约 411 期/日估算单版本未压缩输入：

保存来源数一年共享输入估算两年估算
1 个约 60 MiB约 121 MiB
2 个约 92 MiB约 184 MiB
10 个约 348 MiB约 696 MiB

这是当前结构的量级估算，未包含输入修订、段快照、逐笔实验明细、WAL、临时文件或备份；压缩率尚未实测，不据此承诺长期总空间。26 个实验共享同一来源输入，不把上表乘以 26。

真正容易膨胀的是“实验数 × 每日期数”的逐笔结果：500 个版本若每期都触发，30 天明细可能超过现有 1 GiB 预算。因此保留 30 天只是目标，必须加明细配额与分层清理，不能同时承诺满容量 500 个版本和无限细节保留。

7.2 配额和删除顺序

  • 继续以现有目录 1 GiB 为总预算，不默认扩大。启用时估算未来增长；预留约 20% 给输入采集、检查点、事务和归档临时文件。
  • 达到计算软阈值先清可回收明细、暂停新重算/增量计算，为采集留预算；接近总硬预算时明确显示“数据采集暂停”和源删除倒计时，不能静默删未消费输入。
  • 数据库大小与压缩文件必须合并计量。现有 storage_status() 只数目录第一层文件，新建 archives 子目录后须改成受控递归计量，否则会漏算。
  • SQLite DELETE 后的空闲页可复用，但主文件通常不缩小。不能把删除行数当作已回收磁盘；不在业务高峰自动 VACUUM，也不改变上游清理策略。
  • 压缩归档先写临时文件、完整校验行数/哈希并 fsync、原子改名，再提交索引；验证成功后才回收热数据。崩溃后能识别孤立文件或未完成批次，不能推进一个尚未落盘的采集游标。
  • 归档是输入库的一部分，不是备份；模拟库和档案清单需要配套一致备份，保存于预算目录之外。

7.3 防止“刚好来不及保存”

监控最早未覆盖期与上游保留边界的距离。建议剩余 7 天提醒、1 天升级；正常应保持分钟级采集延迟。计算暂停可长期补算，采集进程离线超过上游保留窗口则不能保证恢复未曾保存的数据。若以后要求跨任意长期停机也绝不丢数据，需上游清理前生成持久档案/导出凭证或增加独立存储；那是跨项目增强，不应虚称单个只读采集器已提供此保证。
