异常轮次退出调度，历史账务独立核对

2026-11-27 · 设计基线 43fd8a2 · 规则 13「jnd28 短记忆反向模型 过三关 每天 4 次」

最新原则：一期只有 210 秒。超过原发送截止后，异常轮次自动结束执行，后续仍按原定时窗口启动；未确认账目按原轮次保存并保留本金，后台核对，不再以人工处理作为开新轮的前提。

本版取代之前“先核对旧单再解除调度阻塞”的方案。用户已授权开始修复；本文是施工依据，不代表代码、迁移或生产恢复已经完成。

现有流程缺口自动结束异常轮本金与迟到结算后台核对数据/API本次旧轮验收

1. 现有流程与本次改变

定时开轮→两腿分账 / 一条消息→发送及受理回报→逐腿结算→下一关或闭轮

新轮由自动触发 worker 认领，日额度、run、session、路由 runtime 与首单在同一个写事务建立；轮内后续期由来源同步派发。主辅两腿共用 pending_plan，必须全部处理完成才能正常推进关数。正常轮次可以跨日完成，仍归原开轮日。

当前周期表以“规则 + 方案 + 路由”为主键，只保存一份当前状态。之前的未确认单占着 pending_plan，旧 session 一直 running，导致后续开轮被 cycle_running 拦截。

修复后拆成两个生命周期：执行生命周期在异常期原截止后结束；账务生命周期继续保存、核对并结算历史单。新轮拥有自己的状态，旧单的迟到结果不能覆盖新轮关数、注码或 pending。

2. 已验证的故障与相关缺口

北京时间 11 月 26 日 02:02:24 开轮1937，02:05:18 第一关净盈利3.93；02:05:51 第二关3510978期“双9 大单4”出现 IncompleteReadError。任务64488/64489、流水64481/64482保留未确认，截止已经过去但轮次没有退出。

问题验证修复
连接阶段EOF漏分类模拟connect失败，发送函数未调用，也被标为unconfirmed。按RPC是否开始区分；发送前临时失败可在原窗口重试，发送后未知不盲目重发。
同attempt补成功被去重先unknown再accepted仍保留unknown。独立核对证据入口与追加审计，不放宽原回报幂等规则。
仅作废不会闭轮void后pending清空但session仍running。异常执行收尾有独立的归档与结束逻辑。
cancelled不在周期终态手动停止后可能留下无法推进的pending。只有证明未发送的取消才是零损益终态；人工停止意图不自动解除。
当前表不支持历史并存新轮会覆盖同归属当前快照。增量run/route归档，旧pending完整保留。

实际历史异常阶段没有足够日志，不能由离线复现推出这笔一定没发送。它在恢复调度后仍保留真实的“未确认”账务状态。

3. 到期自动退出执行

  1. 巡检识别原发送截止已过、且本轮存在未确认或发送租约失效的任务。正常placed待开奖本身不触发异常退出，日期变化也不触发。
  2. 锁定用户、规则、方案、run及所有参与路由，在同一SQLite写事务保存完整原状态、策略、pending计划和每笔事件归属。
  3. 某一路由触发时，对同会话全部路由归档；其他已发送待开奖也保存在原档案。取消可证明尚未发送的排队任务；已经发送中或未知的任务保留未知。
  4. 按第4节公式一次性保留本金，结束旧run和路由runtime的发送入口，再清当前session活动指针。原任务、尝试和账务事件不删除。
  5. 若没有独立人工停止/日风控/禁用/迁移阻塞，session回waiting。下一轮重新经过原时段、新信号、冷却、每日及每窗口次数检查，不立即补发。

派单、自动/手动重试、任务领取和发送前最终复核均要拒绝旧run。事务外已经开始的RPC可能仍返回，归档和保留金额承接其后果。

原规则保持：02:01、08:01、14:01、20:01起的四个北京时间窗口，每窗口最多一轮，每天最多四轮。旧日次数不退回，不补错过窗口，不在今天继续昨天的三关进度。

4. 未决本金与迟到结算

保留金额是未决占用，不是假定亏损。当前策略余额不是已核实的目标账户钱包余额，两者不得混用。

记号定义
B原pending.state.balance，即原待处理期开始前余额。
K归档事务时，本期已经settled的腿的实际净盈亏；确认void/cancelled为0。
R本期尚未终态的腿本金之和，包括unknown和placed待开奖。
C = B + K − R异常退出后供chain模式后续轮次继承的可用余额，R只扣一次。
credit = R + N − K全部历史腿结清后，N为该期总净盈亏；此公式得到应释放的本金/返还，避免K重复入账。

credit保存在历史档案，只在下一次新开轮事务消费一次，不修改正在运行的新轮余额、当前注码、关数或pending。派单事务失败时，credit消费也回滚。

现有chain策略会将不足base的余额补到base。本次保留该规则，但明确记录新增本金top_up_amount；不能将补充本金称为旧单已返还。all_in本来每轮独立投入base，历史返还明确记为独立周期返还，不改变新轮base。旧chain信用只允许未来chain轮消费；用户中途切成all_in时保留未应用，不能标为已用却丢失资金。

本次例子：B=22.39，K=0，R=13，C=9.39。下一轮base=10时新增本金0.61，历史13继续保留。旧单若实际输13，credit=0；确认未发则credit=13；净赢5则credit=18。结果只记旧轮并在以后开轮边界释放资金。

旧事件仍使用原赔率快照、原期真实开奖和原统计日。同统计日的真实盈亏仍可触发当天风控；这属于正常风险控制，不能因“旧轮隔离”而屏蔽。禁止的是旧周期直接覆盖新周期的资金过程与关数。

5. 自动核对不占调度时间

  • 执行器优先读取本地持久化的原任务结果，其次按已知消息ID精确读取原目标消息和可信关联回执。
  • 使用原冻结账号、目标、协议、期号与内容。账号session或目标身份变化不能用新身份替查；没有唯一证据就保持未知。
  • 严格协议校验可信机器人、回复关联、原期号、玩法和金额；legacy只确认发送，不伪装为平台受理。历史不透明轮号必须有原期证据映射。
  • 无消息ID、查无消息、相同文本多条或取数失败都不能认定“没下注”。后台限次退避，历史状态保持未决，后续调度照常评估。
  • 只读核对不发送试探消息；与正常发送分开预算、使用账号锁，单次有界。核对网络请求不占数据库写事务。
  • 有效迟到证据通过独立接口追加审计，整组主辅任务原子更新。已接受结果不被unknown覆盖，矛盾证据进入冲突记录，不静默翻转已结账事实。

人工只用于最终账务争议，既不是每期投注动作，也不是未来定时开轮的必经步骤。修复不要求先把本次13元判成输或未发。

6. 数据、API与显示

新增auto_trigger_cycle_archives，唯一键(rule_run_id,route_id)。保存原归属、统计日、期号、完整state/policy/pending、K/R、保留金额、待应用credit、应用到的新run和审计时间。当前周期主键不变。

归档状态为awaiting_reconciliation、awaiting_settlement、resolved。已经resolved但credit未消费的档案仍需保留；日常清理、删除规则/方案/路由不得丢失未决事件归属或返还权。

接口作用与约束
GET /api/platform/auto-trigger-rules/{id}/cycle-recoveries用户授权内的历史归档列表，有界分页，纯只读。
GET /api/executor/reconciliations/pull领取有界核对任务，沿用现有executor认证与pull惯例；只写独立核对租约，没有发送资格。
POST /api/executor/jobs/{id}/reconcile原attempt身份+核对租约+证据；unknown只退避，可信送达/受理/拒绝单调推进，追加审计。

规则现有cycle_runtime增量返回未决历史轮数、保留本金、待应用credit、最近异常run/时间/原因；路由也显示自身保留金额。页面应表达“当前等待下一窗口；旧轮执行已结束，历史投注待核对”，不再只显示running，也不给过期任务重发按钮。

执行器最小核对契约

pull项复用原job DTO，加reconciliation_token、original_attempt及delivery_evidence。原target/account/protocol来自冻结identity，不提供新的发送attempt_token。

reconcile含reconciliation_token、original_attempt_token、outcome、evidence、reason。首版outcome限unknown、transport_confirmed、accepted、rejected。无证据的not_sent不开放。远端查证和财务应用分离，组级证据和所有者在事务中复核。
